## 使用方式

- Ubuntu 22.04 安裝 Docker Engine 與 Compose plugin；Windows／macOS 安裝並啟動 Docker Desktop 的 Linux containers。
- 下載符合 CPU 架構的完整套件並解壓縮；樹莓派選 `linux-arm64`，Apple Silicon 選 `macos-arm64`。
- Windows 執行 `./taiphoon_agent.exe start`；macOS／Linux 執行 `./taiphoon_agent start`。
- 首次啟動會引導設定、校驗並載入內附映像；操作者另外下達 Arm 與起飛命令。
- 進階設定見套件內的 `README.md`。重新起飛後須重新下達編隊命令；地面 MOVE／FORMATION 命令不排隊。

## 主要變更

相較於 v1.3.0-rc.3：

- 修正降落或解除解鎖後保留舊編隊的問題：清除任務目標、編隊 Epoch／槽位與執行軌跡，重新起飛不會恢復舊任務。
- 修正降落後持續規劃與地面佔位的問題：停止移動規劃與佔位廣播，其他 Agent 依有效落地狀態移除該機的舊軌跡與編隊資格。
- 修正地面延遲軌跡重新寫入控制器快取的問題，並拒絕舊 Epoch 在重新起飛時自動恢復編隊。
- 修正重新下達垂直編隊命令時，保留既有編隊高度偏移。
- 調整編隊與同儕避碰的預設機體中心最小距離為 2 m，規劃額外裕度維持 1 m。
- 修正原生啟動器的容器清理：Agent 退出後移除對應完整容器 ID；stop／restart 清理停止的容器，保留資料卷。
- 調整預設測試，只建置現行控制鏈與必要回歸；舊模型測試可由 `TAIPHOON_BUILD_LEGACY_TESTS=ON` 啟用，原始檔保留。
- 新增 Windows 原生 Docker 三機小場域驗證、PX4 ULog 查核，以及依實際 cubic 曲線判定場域邊界的驗收工具。
- 新增兩種 Linux 架構的降落／重飛節點回歸與曲線邊界回歸至多平台容器驗證流程。

## 驗證與限制

- 發布前 Windows Docker workspace：254 個單元測試、降落／重飛 ROS2 planner 節點回歸與三組 launcher CTest 通過；Windows 原生啟動器已在 Docker 內交叉編譯並驗證退出清理。
- 新版三機 SITL／Agent 的有效飛控狀態、未解鎖落地狀態、地面無軌跡／佔位與 GCS ROS2 訂閱已確認；完整實際降落再起飛驗收仍待操作者測試。
- 多平台 Release workflow 在 Linux AMD64／ARM64 驗證 ROS2、launcher、runtime 健康；AMD64 驗證 CLI 單組／四組 PX4 啟動與停止；Windows／macOS 編譯原生啟動器。只有所有必要工作通過才發布五個完整套件。
- 小場域失效機與交叉移動安全驗收仍未通過：停止 Agent 2 後，PX4 ULog 顯示剩餘兩機曾接近至約 1.80 m；交叉移動的預計曲線曾超出 9 m 場域邊界。本版 2 m 設定仍需依機體與定位誤差驗收。
- 9×9×8 m 場域尚無 runtime 邊界限制；RTL 未納入本次飛行驗收，PX4 原有失聯返航行為維持。硬體、樹莓派／macOS 現場飛行仍需驗收；macOS 套件尚未公證，ARM64 的 PX4 模擬需要 Docker 支援 AMD64 CPU 模擬。
- 詳細證據見 [降落生命週期驗證](../codex/landing-mission-lifecycle-report.md) 與 [三機小場域驗證](../codex/small-field-three-agent-validation-report.md)。
